# Location: docs site

Pages built and served by a site framework. This file covers the framework's mechanics: where pages go, navigation, front matter and the build check. How to write for the reader is in `user-docs.md`.

## Follow the framework

Read the site's config before you add a page. Navigation and page metadata are the framework's, not yours to invent.

| Framework | Found by | Pages | Navigation | Build |
|---|---|---|---|---|
| Starlight | an Astro config that loads `@astrojs/starlight` | `src/content/docs/`, front matter needs `title` | the `sidebar` in the Astro config, unless it is autogenerated | the `build` script in `package.json` |
| Docusaurus | `docusaurus.config.*` | `docs/` | `sidebars.*` | the `build` script; fails on broken links when `onBrokenLinks` is `'throw'` |
| MkDocs | `mkdocs.yml` | `docs/` | `nav` in `mkdocs.yml` | `mkdocs build --strict` |
| VitePress | `.vitepress/config.*` | the configured source folder | `sidebar` in the config | the `build` script |
| mdBook | `book.toml` | `src/` | `src/SUMMARY.md` | `mdbook build` |
| Sphinx | `conf.py` | the source folder | `toctree` directives | `sphinx-build -W` |

This table was written from the frameworks' documented behaviour and checked against one Starlight site. Confirm each cell in the site's own config and scripts before you rely on it.

- Match the front matter of the existing pages: the same keys, the same style of `title` and `description`.
- A new page is added to the navigation in the same change. A page that the navigation does not reach is unfinished.
- Link the way the existing pages link (site-absolute paths or relative files). Do not mix.

## Code and docs in different repos

Take two paths: the source repo and the docs repo.

- Read and check every claim in the source repo.
- Write only in the docs repo.
- Keep `docs-map.txt` at the docs repo root. Its `source` line is the source repo's remote URL, its `verified-at` is a source commit, and its source paths are relative to the source repo root.
- Run `scripts/docs-scope --source <source repo path>` from the docs repo.
- The two repos are released separately. If the site documents the latest release and the source checkout is ahead of it, check against the release tag and say which commit you used.

## Command reference for a CLI

Generate it from the help output; do not write it by hand. Build the CLI from the source commit, capture `--help` for the top level and for every subcommand, and write the reference page from that output. Record the regenerating command on the page or in the map's `ledger` line. A hand-written recipe page can sit beside it.

## Check

Build the site with its own build command. Treat every warning and every broken link as a failure, and fix it or report it. Then:

```sh
scripts/check-links --site-root <content folder> --source-root <source repo path> <content folder>
```

`--site-root` checks links that start with `/` against the content folder. If the build cannot run here (missing dependencies, no network), the outcome is blocked for the build check; say so, and report what `check-links` found.
